## 추가 발견과 수정 확인

### 5. [P2, 수정 확인] Scene 일시정지 중 놓친 손 떼기 때문에 복귀 후 이전 제스처가 재사용되었습니다

- 위치: `src/BoardScene.ts:12`, `src/BoardScene.ts:27`~`40`의 `down` 및 입력 핸들러, `src/main.ts`의 `switchView()`.
- 원인: `down`은 동일 포인터의 `pointerup` 또는 활성 상태에서의 `gameout`으로만 비워집니다. Scene 일시정지 시 제스처를 정리하는 핸들러가 없습니다. 설치된 Phaser의 `src/input/InputPlugin.js`에서 `update()`와 `onGameOut()`은 `isActive()`가 거짓일 때 이벤트를 전달하지 않으며, `src/scene/Systems.js`의 `canInput()`은 일시정지 상태를 제외합니다. 따라서 일시정지 중 첫 손가락을 떼면 기존 `down`이 남을 수 있습니다.
- 수동 재현 방법: 첫 손가락을 타일 (0,0)에 누른 상태로 두 번째 손가락으로 마을 탭을 누릅니다. 마을에서 첫 손가락을 떼고 퍼즐로 돌아온 뒤 같은 포인터 ID가 재사용되는 손가락으로 (0,1)을 제자리 탭합니다. 이전 누르기 상태가 남으면 새 `pointerdown`이 무시되고 새 `pointerup`이 (0,0)에서 시작한 스와이프로 처리됩니다.
- 실행 근거: 실제 입력 핸들러에 `pointerdown({id:1,x:44,y:44})`를 전달하고, Phaser의 일시정지 동작처럼 놓기 이벤트 전달을 생략한 뒤, 복귀 후 `pointerdown({id:1,x:100,y:44})`, `pointerup({id:1,x:100,y:44})`를 전달했습니다. 제자리 탭인데 `attempt({row:0,col:0},{row:0,col:1})`가 호출되었습니다. Phaser의 이벤트 차단 근거와 핸들러 동작을 함께 확인했으며, 실제 Android 제스처 전달/포인터 ID 재사용은 추가 검증이 필요합니다.
- 영향: 복귀 후 첫 제자리 탭이 의도하지 않은 교환을 요청할 수 있습니다. 다른 포인터 ID로만 조작하면 이전 제스처를 소유한 ID의 놓기가 올 때까지 입력이 무시될 수 있습니다.
- 수정 확인: 루트 작업에서 Scene의 PAUSE/RESUME/SLEEP/SHUTDOWN 이벤트에 제스처 취소 처리를 추가했습니다. 후속 요청에 따라 모의 Phaser에 Scene 이벤트를 구현하고 다섯 번째 회귀 테스트로 네 이벤트의 `down`·선택 해제와 복귀 후 정상 탭을 확인했습니다. `src` 수정은 루트에서 수행했으며 이 검토 세션에서는 테스트와 문서만 수정했습니다. 게임 전체 백그라운드 전환은 Scene pause와 같다고 가정하지 않고 아래 실기기 검증 항목으로 유지합니다.

## 최초 발견 기록 (수정 전)

### 1. [P1] 이전 스테이지 결과가 새 스테이지에 적용됩니다

- 위치: `src/main.ts:62`의 `startLevel()`, `src/main.ts:67`의 `onMove`, `src/main.ts:77`의 `finish()`, `src/main.ts:111`의 재시작 핸들러. 관련 조건은 `src/BoardScene.ts:107`의 `canLeave()`입니다.
- 원인: 종료 시 `setTimeout(() => finish(won), 300)`은 승패만 보관합니다. `finish()`는 실행 시점의 전역 `currentLevel`과 `save`를 읽습니다. 타이머를 취소하거나 플레이 회차를 확인하는 코드가 없습니다. `stopPlaying()`은 `finished`를 설정하지만 `canLeave()`는 `busy`만 확인하므로, 이동 처리 반환 후 결과 창이 뜨기 전에는 재시작·화면 이동·스테이지 선택을 할 수 있습니다.
- 재현 방법: 스테이지 1을 이미 완료하여 2가 열린 상태에서 1을 다시 플레이합니다. 승리하는 마지막 이동의 연쇄가 끝나고 결과 창이 뜨기 전 300ms 안에 마을로 이동하여 2를 선택합니다. 이전 1의 승리 타이머가 2를 완료 처리하고 별·코인을 지급하며 3을 열 수 있습니다. 더 간단히 승리 직후 재시작을 누르면 새 보드에 이전 결과 창이 표시됩니다.
- 실행 근거: 실제 `onMove([12,10,0,0,0,0],220)` 실행 후 `startLevel(2)`를 호출하고 예약된 300ms 콜백을 실행했습니다. `save.completed[0] === 2`, 새 스테이지의 `score === 0`, 새 Scene의 `finished === false`인데 승리 창이 열렸습니다. 이 검증은 최소 상태에서 전역 스테이지 오염을 확인한 것이며, 위 정상 저장 진행 경로에서도 같은 함수를 사용합니다.
- 영향: 플레이하지 않은 스테이지 완료·보상·해금이 저장될 수 있습니다. 실패 직후 재시작해도 새 보드 위에 이전 실패 결과가 나타납니다. 초기화를 사이에 수행하면 이전 승리가 초기화된 저장 상태에 다시 기록될 수 있습니다.
- 최소 해결 방향: 결과 타이머를 보관하여 `startLevel()`과 초기화 시 취소하고, 결과에 스테이지 ID와 플레이 회차 ID를 함께 전달해 현재 회차와 일치할 때만 적용해 주세요. 결과 대기 상태에서 재시작·스테이지 선택을 막거나 해당 조작이 이전 결과를 명확히 취소하도록 해 주세요.

### 2. [P2] 다른 화면에서 뜬 결과 창의 ‘다음/재시도’가 퍼즐 화면으로 이동하지 않습니다

- 위치: `src/main.ts:85`의 `#result-next` 핸들러, `src/main.ts:101`의 `switchView()`.
- 재현 방법: 마지막 이동 처리가 끝난 뒤 300ms 안에 마을 또는 설정으로 이동합니다. 그 화면 위에 결과 창이 뜨면 ‘다음’ 또는 ‘재시도’를 누릅니다.
- 실행 근거: 실제 `onMove()` → `switchView('village')` → 결과 타이머 실행 → `#result-next.onclick()` 순서를 실행했습니다. 새 스테이지는 2로 바뀌지만 `route === 'village'`, `#puzzle-view.hidden === true`가 그대로 남았습니다.
- 원인과 영향: 버튼은 `dialog.close()`와 `startLevel()`만 실행합니다. 새 게임은 생성되지만 표시 화면은 마을/설정에 남아 버튼이 진행되지 않은 것처럼 보입니다. 퍼즐 탭을 다시 눌러야 복구됩니다.
- 최소 해결 방향: 결과 버튼에서 스테이지 시작과 함께 퍼즐 화면으로 전환해 주세요. 1번의 결과 회차 보호와 함께 처리하고, 결과 창이 어떤 화면에서 열렸든 버튼이 목적 화면을 표시하는 회귀 테스트를 추가해 주세요.

### 3. [P2] 두 손가락의 좌표가 섞여 의도하지 않은 교환이 발생합니다

- 위치: `src/BoardScene.ts:27`의 `pointerdown`, `src/BoardScene.ts:31`의 `pointerup`. `src/main.ts` 게임 설정에서 `input.activePointers: 2`로 다중 터치를 받습니다.
- 재현 방법: 첫 손가락을 타일 (행 0, 열 0)에 누르고 유지합니다. 두 번째 손가락을 바로 오른쪽 타일 (0,1)에 누른 뒤, 첫 손가락을 움직이지 않고 뗍니다.
- 실행 근거: 실제 `create()`가 등록한 핸들러에 `pointerdown({id:1,x:44,y:44})`, `pointerdown({id:2,x:100,y:44})`, `pointerup({id:1,x:44,y:44})`를 전달했습니다. `attempt({row:0,col:1},{row:0,col:0})`가 호출되었습니다. 두 손가락 모두 드래그하지 않았는데 교환이 요청되었습니다.
- 원인과 영향: `down`은 하나뿐이고 포인터 ID를 보관하지 않습니다. 두 번째 누르기가 첫 좌표를 덮어쓴 뒤 첫 손가락의 놓기 좌표를 다른 손가락의 시작 좌표와 비교합니다. 그 교환이 유효하면 이동 횟수와 보드가 의도하지 않게 바뀝니다. 무효여도 불필요한 교환 애니메이션이 발생합니다.
- 최소 해결 방향: 활성 제스처의 포인터 ID를 보관하고 동일 포인터의 놓기만 처리해 주세요. 제스처가 진행 중이면 추가 누르기를 무시하고, 취소·화면 이탈·일시정지 시 제스처 상태를 정리해 주세요.

### 4. [P2] 저장 실패 시 초기화가 성공한 것처럼 보이고 재실행하면 이전 진행이 돌아옵니다

- 위치: `src/state.ts:17`의 `clearSave()`, `src/main.ts:97`의 초기화 핸들러. 비교 대상은 저장 실패를 알리는 `src/main.ts:22`의 `persist()`입니다.
- 재현 방법: 진행이 저장된 상태에서 저장소의 `setItem()`이 예외를 던지도록 오류를 주입합니다. 설정에서 초기화를 확인한 뒤 앱을 다시 로드합니다.
- 실행 근거: 기존 저장 내용에 `highestLevel:4`, 완료 `[1,2,3]`을 두고 `getItem()`은 기존 내용을 반환, `setItem()`은 예외를 던지도록 했습니다. 실제 `clearSave()` 반환은 `highestLevel === 1`이었지만 이어서 실제 `loadSave()`를 호출하면 `highestLevel === 4`였습니다.
- 원인과 영향: `clearSave()`가 `saveData()`의 실패 반환값을 버리고 기본값을 반환합니다. 초기화 핸들러는 이 값을 정상 저장 결과처럼 적용하고 실패 안내도 하지 않습니다. 따라서 이번 세션만 초기화되고 재실행하면 이전 진행이 복원됩니다.
- 최소 해결 방향: `clearSave()`에서 성공 여부를 호출자에게 전달하고, 실패 시 초기화가 저장되지 않았다는 안내를 표시해 주세요. 저장 실패 처리 정책에 따라 기존 메모리 상태를 유지하거나 세션 한정 초기화를 명시해 주세요.

## 테스트 부족 및 추가 검증 지점

1. **화면 전환·스테이지 결과 통합 테스트:** 추가 회귀 테스트는 완료된 1을 재플레이한 뒤 2로 이동하는 타이머 보호, 마을/설정의 승리·실패 결과 버튼, 두 손가락 소유권, 초기화 실패 안내, Scene 이벤트의 제스처 정리를 다룹니다. 실제 Phaser 부팅·Scene 종료·캔버스 크기·브라우저 DOM은 모의 구현이므로 별도 통합 검증이 필요합니다. 결과 대기 중 설정 초기화, 첫 완료 보상의 중복 방지, 결과 창 취소 동작도 자동 테스트 보강 대상으로 남습니다.
2. **일시정지와 앱 생명주기:** `switchView()`는 연쇄 중 화면 이동을 막고 다른 화면에서 Scene을 일시정지합니다. 별도 `visibilitychange`와 Android `appStateChange` 핸들러는 오디오만 직접 제어합니다. Phaser 자체 백그라운드 처리가 있으므로 이것만으로 보드 일시정지 결함이라고 단정하지 않았습니다. 연쇄 애니메이션 중 홈 이동·복귀, 결과 대기 중 백그라운드 전환, Android 뒤로가기 후 복귀에서 이동/수집/결과가 한 번만 처리되는지 실기기로 확인해 주세요.
3. **터치 통합 테스트:** 단일 탭 두 번, 네 방향 스와이프, 보드 밖 놓기, 두 손가락 놓기 순서, 입력 중 Scene 일시정지·재개를 검증해 주세요. 위 3번은 실제 입력 핸들러로 재현했지만 Android 이벤트 전달과 화면 크기에 따른 좌표는 실기기 검증이 필요합니다.
4. **저장 테스트:** `loadSave()`의 잘못된 JSON·버전·범위값·중복 완료 목록 정리, 저장소 읽기/쓰기 실패, 초기화 실패, 재실행 후 진행·언어·음악/효과음 복원을 검증해 주세요. 현재 저장 구조에는 진행 중 보드·남은 이동·수집량이 없고 시작 시 `highestLevel`로 새 게임을 만듭니다. 플레이 중 재실행 시 재시작하는 정책인지 확인하고 그 정책을 테스트해 주세요. 중간 저장을 요구받지 않았으므로 그 자체는 결함으로 집계하지 않았습니다.
5. **오디오 테스트:** `AudioManager`는 지연 생성, 음소거, 보이스 제한, visibility 및 네이티브 중단 복구 코드를 갖추지만 자동 테스트가 없습니다. 지원되지 않는 AudioContext, `resume()` 거부 후 다음 사용자 입력 재시도, `suspend()`/`resume()` 경합, 음소거 전환 중 예약 음 제거, `destroy()` 이후 타이머·노드 정리를 검증해 주세요. 읽기만으로 별도 확정 결함은 찾지 못했습니다.
6. **엔진 보강:** 기존 테스트는 초기 생성, 무효 교환 복구, 특수 생성/조합, 수집량, 낙하 스냅샷, 상수 난수 종료를 다룹니다. 자동 막힘 해소의 `removed: []` 단계가 목표/점수를 증가시키지 않는지 명시적으로 검증하고, 불가능한 셔플 구성의 새 일반 보드 대체 및 잘못된 보드 크기/난수 입력 오류도 보강할 수 있습니다. 현재 검사 결과만으로 엔진에 새 확정 결함을 보고하지는 않습니다.
